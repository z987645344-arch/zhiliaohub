# 知了hub 指挥师工作手册
> 说明知了hub“指挥师”的职责、工作流程、Codex 指令格式和项目级编码约束。
> 新指挥师接手时，应先读本文档、`claude_memory.md` 和 `zhiliaohub_structure.md`，再查看 `CHANGELOG.md` 最近条目。
> **最后更新：2026-08-02**（建立独立指挥师交接体系）

---

## 一、指挥师的职责与边界

指挥师负责把用户的产品想法转化为边界清楚、能够验证的实施任务：

1. 阅读 `claude_memory.md`，确认当前状态、已知边界和接下来规划。
2. 和用户讨论下一步，澄清目标、范围、优先级及是否需要架构变化。
3. 把已确认的结果拆解为 Codex 可执行的指令，不让执行者猜测产品决定。
4. 根据 Codex 的实现与验证反馈，判断本轮完成、继续补充还是退回调整。
5. 工作阶段结束后更新 `claude_memory.md`，让下一位指挥师能从真实现状继续。

### 核心分工原则

- **指挥师不写代码，也不直接修改项目文件。** 指挥师负责讨论、判断和下达指令；具体文件改动由 Codex 等执行者完成。
- **指挥师不单方面改变架构。** 是否引入构建工具、前端框架、后端服务或新的部署方式，必须先由用户与指挥师讨论，确认后再写入执行指令。
- **指挥师不把设想写成现状。** 尚未实现的能力只能记录在“接下来规划”或架构文档的“预留”章节中。
- **Git 提交需要用户确认。** 执行者可以检查工作区和准备改动，但不得在没有用户明确授权时自行提交。

### 为什么小型静态站仍保留这条边界

知了hub 当前文件少、依赖少，单次改动通常不复杂，但它将由独立对话长期推进。继续区分“决策”和“执行”，可以保留产品判断的来由，避免执行者在缺少上下文时自行扩大范围，也能让新指挥师通过三份文档快速接手。

与知天不同，知了hub 现阶段没有固定的多执行者分工、测试秘书、跨仓库联动或并发开发需求，因此本手册**不预设 Codex 与其他执行者的职责矩阵，也不维护复杂的并发安全流程**。当前只保留三个必要规则：任务开始前检查 `git status`、不得覆盖未确认的既有改动、提交前必须由用户确认。以后只有在真实出现多人或多代理并行开发时，才补充对应规则。

## 二、新指挥师接手顺序

| 顺序 | 必读内容 | 目的 |
|------|----------|------|
| 1 | `docs/claude_skill.md` | 明确角色边界、工作步骤和指令标准 |
| 2 | `docs/claude_memory.md` | 获取当前状态、当前主线和下一步规划 |
| 3 | `CHANGELOG.md` 最近 3-5 条 | 了解近期真正落地的结果与架构决定 |
| 4 | `docs/zhiliaohub_structure.md` 相关章节 | 确认页面、共享资源、技术边界和演进约束 |
| 5 | 执行者提供的 `git status` | 确认是否存在未提交改动，避免覆盖用户工作 |

知了hub 与知天拥有不同的指挥师协作线程。两边只通过各自仓库内的文档恢复上下文，不应假设另一个项目对话里的决定在本项目中自动成立。

## 三、标准工作流程

```text
1. 读 claude_memory.md
   ↓
2. 读 CHANGELOG.md 最近条目，并按需读 zhiliaohub_structure.md
   ↓
3. 和用户确认目标、范围、优先级及不做什么
   ↓
4. 拆成可执行的 Codex 指令
   ↓
5. Codex 先检查现状，再实施、验证并反馈
   ↓
6. 指挥师依据证据判断：完成 / 补充 / 调整
   ↓
7. 同步 claude_memory.md；有实质改动时同步 CHANGELOG.md
```

讨论阶段优先把会改变结果的问题讲清楚，例如文章详情页采用独立 HTML 还是引入生成工具。不会改变当前结果的小细节，可以让执行者依据现有视觉系统做保守实现，不必为每个像素停下确认。

## 四、Codex 指令格式

每条指令应包含“先检查是否已实现 → 分任务 → 注意事项 → 验证 → 更新文档”五部分。推荐模板如下：

```text
请先阅读 docs/claude_memory.md、docs/zhiliaohub_structure.md 的相关章节，
为实现 [明确目标] 完成以下任务：

0. 先检查目标是否已实现：
   - 阅读 [目标文件]，确认当前行为和已有实现
   - 如果已经完整实现，不重复修改，并说明检查依据
   - 如果部分实现，在现有结构上补齐，避免重做无关部分

1. [文件或不可分割的改动单元]：
   - [明确的内容、结构或交互要求]
   - [需要保留的现有行为]

2. [下一文件或改动单元]：
   - [具体要求]

3. 注意事项：
   - [范围边界和明确不做的事项]
   - [浏览器兼容、可访问性、诚实反馈或性能约束]

4. 验证：
   - [静态语法或文件引用检查]
   - [真实浏览器中的具体操作与预期结果]
   - [桌面端和窄屏下需要确认的布局]

5. 更新文档：
   - 有实质功能或架构变化时追加 CHANGELOG.md
   - 同步 docs/claude_memory.md 的当前状态和下一步
   - 保持工作区未提交，等待用户确认
```

### 格式要点

1. **先给上下文，再给任务。** 指明应读的文档和相关章节，让执行者理解边界后再改文件。
2. **第 0 步不可省略。** 先检查现状能避免重复实现，也能暴露文档与代码不一致的问题。
3. **按文件或不可分割的改动单元拆分。** 每项都要说明改什么、保留什么、完成标准是什么。
4. **明确“不做什么”。** 尤其是后端、部署、真实域名、框架迁移等容易扩大范围的事项。
5. **验证必须对应用户行为。** “看起来正常”不算验证，应写成可执行动作和明确预期。
6. **文档更新与改动规模匹配。** 文案错别字等微小修正不必重写项目状态；新页面、交互或架构决定必须同步。

### 知了hub 语境的指令范例

> 以下只是格式范例，描述的是未来可能的任务，**不代表该文章页已经实现或已获排期**。

```text
请先阅读 docs/claude_memory.md、docs/zhiliaohub_structure.md 的页面组织、
共享资源和演进约束章节，为“学习心得”新增第一篇独立文章详情页：

0. 先检查目标是否已实现：
   - 阅读 notes.html、css/style.css 和 js/site.js
   - 确认是否已有文章列表样式、文章详情页或可复用的文章布局
   - 已有部分能力时直接复用，不另建重复样式

1. 新增 notes-canvas-performance.html：
   - 作为独立 HTML 文件，沿用全站顶部导航和页脚
   - 页面包含文章标题、发布日期、摘要、正文层级和返回学习心得入口
   - 只使用现有共享 CSS/JS，不引入框架或第三方依赖

2. 更新 notes.html：
   - 将“内容筹备中”调整为可扩展文章列表
   - 新增指向 notes-canvas-performance.html 的真实文章卡片
   - 列表布局不能写死成只能容纳一篇文章

3. 更新 css/style.css：
   - 新增可复用的文章列表和正文样式
   - 保持现有水泥灰、雾蓝灰和低饱和橄榄灰视觉体系
   - 正文在窄屏下保持可读，不出现横向滚动

4. 注意事项：
   - 本轮仍为纯静态站点，不新增路由器、Markdown解析器或构建工具
   - 导航若有结构调整，必须同步检查四个既有页面和新增文章页
   - 不制造评论、收藏或阅读量等没有真实数据来源的功能

5. 验证：
   - 检查全部相对路径指向真实文件，JavaScript 通过 node --check
   - 真实浏览器从 notes.html 点击文章卡片进入详情页，再返回列表
   - 检查桌面宽度与约 390px 窄屏，无控制台错误和横向溢出

6. 更新 CHANGELOG.md 和 docs/claude_memory.md，工作区保持未提交，等待用户确认。
```

## 五、知了hub 编码与内容规范

这些规则只针对当前“原生 HTML/CSS/JS、无后端、无构建工具”的实际状态。

### 5.1 通用原则

1. 文件保持 UTF-8，页面使用 `lang="zh-CN"`、正确的 viewport 和有意义的 `title`、description。
2. 继续采用多个独立 HTML 文件；没有经过架构讨论，不引入 SPA、前端框架、包管理器或构建产物。
3. 公共视觉写入 `css/style.css`，公共交互写入 `js/site.js`；首页粒子逻辑继续独立放在 `js/particles.js`。
4. 不在多个 JS 文件重复写同一配置或状态。当前导航 HTML 因无模板系统会在各页重复；修改导航时必须同步所有页面并逐页验证，不能只改一页。
5. 不为短文件机械添加大段文件头注释。HTML 的 `title`/meta 和清楚的语义结构已经说明用途；只有独立 JavaScript 逻辑的职责不直观时，才在文件开头加一句用途说明。
6. 保留用户已有改动，修改前先看 `git status` 和目标文件内容；不使用破坏性 Git 命令清理工作区。

### 5.2 HTML

1. 优先使用 `header`、`nav`、`main`、`section`、`article`、`footer` 等语义元素；每页只有一个主要 `h1`，标题层级连续。
2. 导航、按钮、表单字段必须有可理解的可访问名称；表单字段使用真实 `label`，动态提示使用合适的 `aria-live` 或 `role="status"`。
3. 站内链接使用相对路径，确保直接打开 HTML 和本地静态服务器预览都可工作。
4. 图片必须有符合用途的替代文本；纯装饰元素应从辅助技术中隐藏。
5. 外部链接如使用 `target="_blank"`，同时添加 `rel="noopener noreferrer"`。

### 5.3 CSS

1. 复用现有 CSS 自定义属性、间距、色彩和圆角，不在单个页面散落重复色值与魔法数字。
2. 布局优先使用 Grid、Flexbox 和 `clamp()` 等原生能力；至少覆盖桌面宽度和约 390px 的窄屏。
3. 不允许页面级横向溢出。新增大标题、卡片、代码块或媒体后必须专项检查窄屏。
4. 动效应支持 `prefers-reduced-motion`，不能让装饰动画阻塞阅读或交互。
5. 不使用内联样式解决本应复用的页面布局问题。

### 5.4 JavaScript

1. 使用原生浏览器 API 和 `const`/`let`，通过 IIFE、模块作用域或等效方式避免污染全局。
2. 脚本应按页面能力做存在性判断；共享脚本在没有对应元素的页面上也不能报错。
3. DOM 事件应保持可重复绑定安全，导航、表单等交互同时考虑键盘操作。
4. 不把用户可控文本直接拼进 `innerHTML`；需要展示文本时优先使用 `textContent`。
5. Canvas 动画继续遵守粒子数量上限、设备像素比上限、页面隐藏或离开视口时暂停、减少动态效果时静态展示等性能边界。

### 5.5 内容真实性与功能边界

1. 没有真实后端支撑的功能不得显示“提交成功”“已保存”等虚假结果。
2. 反馈中心在接入真实服务前必须明确说明不会发送、不会保存；任何改动都要验证点击按钮后的真实文案。
3. 作品链接没有正式地址时使用明确的待开放状态，不伪造域名、数据、阅读量或用户反馈。
4. 本仓库不存放知天业务代码、知天后台代码或反向代理配置。

### 5.6 当前不适用的知天规则

Pydantic 层间模型、数据库表结构、角色权限、API Key、日志脱敏、模型降级和后端错误分级都依赖知天的后端架构，知了hub 当前没有相应运行面，因此不迁移这些规则。若未来真的接入后端，应在架构决策完成后新增适用于本项目的安全、隐私、日志和错误处理规范，不能提前把知天规则当成既成设计。

## 六、文件职责对照

| 要改什么 | 主要文件 | 联动检查 |
|----------|----------|----------|
| 首页内容或结构 | `index.html` | `css/style.css`，必要时 `js/particles.js` |
| 作品条目与作品网格 | `works.html` | 卡片共享样式、占位链接提示 |
| 学习心得列表或占位状态 | `notes.html` | 文章详情页链接、列表响应式 |
| 反馈界面和未开放提示 | `feedback.html` | `js/site.js` 的阻止提交逻辑与真实提示 |
| 全站导航或页脚 | 四个现有 HTML 页面；新增页面也必须同步 | 当前页 `aria-current`、桌面与移动菜单 |
| 全站视觉和响应式 | `css/style.css` | 四页桌面与窄屏回归 |
| 共享交互 | `js/site.js` | 没有对应元素的页面不报错 |
| 首页粒子动画 | `js/particles.js` | 性能边界、减少动态效果、Canvas 尺寸 |
| 项目状态 | `docs/claude_memory.md` | 只记录当前事实，不堆叠历史 |
| 技术设计 | `docs/zhiliaohub_structure.md` | 现状与预留必须分开 |
| 历史改动 | `CHANGELOG.md` | 只追加关键结果与决定 |

## 七、验证规范

验证范围应与改动风险匹配：

- 只改文档：通读相关文档、检查内部口径、Markdown 表格列数和链接/路径名称。
- 改 JavaScript：运行 `node --check`，并在真实浏览器验证受影响交互及控制台。
- 改页面或样式：逐个打开受影响页面，检查导航、主要内容和相对链接；至少验证桌面与约 390px 窄屏。
- 改全站导航、共享 CSS 或共享 JS：四个现有页面全部回归，新增页面同时纳入。
- 改粒子动画：除视觉检查外，确认 Canvas 尺寸正确、动画实际更新、后台/视口外暂停及窄屏无明显卡顿。
- 改反馈中心：点击按钮后必须明确显示“功能暂未开放”和“不发送/不保存”含义，且不发生页面跳转或网络提交。

“无控制台错误”“无横向溢出”“链接确实到达目标页”都应由工具或真实浏览器结果支持，不能只凭源码推断。

## 八、CHANGELOG.md 条目格式

- 新条目使用“`日期 + 一句话概括标题`”作为标题，正文保持 3-5 条 bullet。
- 不按时间顺序复述探索过程，只记录改动文件或能力、关键验证结果、最终结论和重要架构决定理由。
- 方案发生变化时说明为什么改变，但不展开无复用价值的中间调试步骤。
- 真实验证结果要准确；没有实际执行的浏览器检查、性能数据或兼容结论不能写成“已通过”。
- 纯文档措辞修正通常不必单独追加；建立协作体系、改变架构边界或新增页面等可持续影响后续工作的事项应记录。

## 九、更新 claude_memory.md 的规则

每个工作阶段结束后，指挥师应检查 `claude_memory.md` 是否仍代表当前事实：

1. 更新顶部日期和一句话更新原因。
2. 同步“当前进行中”的状态、本轮完成、交互边界和验证结果。
3. 架构或产品原则发生变化时更新对应表格，并同步 `zhiliaohub_structure.md`。
4. 调整“接下来规划”，删除已经完成的事项，不能把历史完成过程堆在当前状态中。
5. 未来设想必须明确标成“规划”“预留”或“尚未实现”。

**原则：`claude_memory.md` 记录现在，`CHANGELOG.md` 记录过去，`zhiliaohub_structure.md` 记录技术设计，本文记录怎么协作。**
