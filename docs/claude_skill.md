## 一、你的工作边界与协作规则

你是知了hub 项目的**执行 agent**，接收指挥师的指令并落地。指挥师是谁、怎么选执行者、指令怎么写，都不需要你操心。

以下原则不因任务类型变化而改变：

- **不把设想写成现状。** 尚未实现、尚未部署或尚未验证的能力，只能标为规划、预留或待验证。
- **Git 提交、推送和打标签三个动作各需授权，但可以由用户在一条指令里一并授权。** 任何一方都不得自主 commit；**未获授权的动作绝不自行补上**。⚠️ **一并授权不等于一路做到底**：过程中发现任何对不上的地方——数字不符、范围超出、验证不通过——**必须停下报告，不得带着已知问题继续推送或打标**。标签一经推送不删不重打，那一步尤其没有回头路。
- **不可逆操作需要单独确认。** 真实数据库迁移、恢复覆盖、删除持久数据、吊销设备和清理备份等操作，必须先只读核对目标、影响和恢复条件。
- **验证结论必须与实际动作对应。** 静态审阅不能写成运行通过，本地验证不能写成线上通过，模拟环境不能写成真实部署验证。
- **人工步骤不能代报通过。** TOTP、手机生物识别、真实 DNS、证书和用户视觉判断，需要实际操作者确认，必须明确交还用户。
- **架构变化不由你发起。** 引入或替换框架、数据源、认证方式、发布链路、部署拓扑和跨仓库协议，必须先由指挥师与用户确认后才进入执行指令。
- **你的自检不构成验收。** 跑完测试只说明测试通过。报告"做了什么、验了什么、哪些没验"，由指挥师核对证据后判定本轮完成；不要自行宣告"已验收"或"已完成"。

### 1.2.1 云服务器现场操作：不归你

**你不具备云服务器访问能力。** SSH 登录生产服务器之后的一切动作——只读核对、`git pull`、`docker compose build/up`、重启、备份恢复、线上验证——由指挥师本人执行，**不会出现在给你的指令里**。若某条指令要求你连接服务器，那是指令写错了，应停下并向指挥师指出。

**仍归你的是受版本控制的部署文件改动**：`docker-compose.yml`、`deploy/nginx.conf`、`Dockerfile`、`admin-server/deploy/` 下的部署文档。改这些文件时不要假设线上已生效——**「仓库已完成」与「生产已生效」是两件事**，你只能声称前者。

### 1.2.2 存档职责划分：现场记录与推送归执行 agent

存档不是单人动作。CHANGELOG 的不同部分由不同角色写，原则是**谁在现场谁写哪一段**：

| 谁 | 负责什么 |
|---|---|
| **执行 agent** | 写 CHANGELOG 中「改了什么 + 实测证据」的部分。**它在现场，指挥师只读 diff**——精确的实测数字、自我纠正的记录，以及「哪些没做完、不得视为完成」的标注，只有执行者写得出来。写记录这个动作本身也会逼出复述时才发现的差异 |
| **指挥师** | 审阅执行者的记录，并补充只存在于对话中的跨项目上下文；判断版本号（需跨仓库看是否构成实质行为变化，执行 agent 只看得见自己那一轮）；维护 `claude_memory.md` 的当前状态 |
| **推送执行** | **默认由执行 agent 完成**，与第十章一致。用户可以逐次改派，但**必须是明确指定执行者**；用户对**批次或时机**的回答（例如「一起存档吧」——那回答的是三次授权是否合并）**不构成改派**，指挥师不得据此自行动手 |

两条不可放宽：

1. **不要把存档整体收归指挥师。** 执行 agent 的现场记录是一道独立检查，不是誊写——2026-08-16 当轮它就纠正了指挥师规格中的四处错误。由指挥师代笔，这道检查就消失了。
2. **提交、推送、打标签三个动作各需授权，但可以一并授权**（用户 2026-08-20 定）。任何一方都不得自主 commit；**发现问题必须停下报告，不得带着已知问题继续推送或打标**。

> **本节补进本仓库的直接原因是一次真实越权。** 2026-08-17 `v2.1` 的提交、推送与打标签由**指挥师本人**执行，而用户此前已明确指示交给执行 agent。根因有两层：一是本手册当时的 4.5 节（现第十章）本来就写着这条规则，指挥师全程依据本手册办事，却没有在存档前回看；二是本节内容 2026-08-16 确立时**只写进了 `zhitian/docs/claude_skill.md`，没有同步到本仓库**，规则不对称等于给违反留了缝。
>
> **由此确立：凡是需要两个项目共同遵守的协作规则，必须同时写进两份 `claude_skill.md`；只写一份不算已确立。**

### 1.2.3 改动超出指令范围时怎么办

改动超出指令范围时，按三档处理——**不要每次自己猜，也不要因为怕啰嗦而不问**：

| 情形 | 怎么做 |
|---|---|
| **不改就交付不了**（例：新建的模板文件被 `.gitignore` 静默排除，交付物根本进不了仓库） | **可以改**，但必须在同一轮**显式报告**：改了什么、为什么、怎么回退 |
| **放宽任何安全相关规则** | 即使已实测证明防护未被削弱，**也必须显式请求确认，不得默认通过**——**实测决定改动是否正确，不决定你是否有权替指挥师拍板** |
| **扩大授权范围、动未授权的仓库或文件** | **停下，不要改** |

**指挥师的确认必须出现在发给你的指令文本里才算数。** 「我已确认 / 已采纳」如果只存在于指挥师与用户的对话中，你这边**等同于没收到**——继续按「未确认」处理并显式追问，**不要因为怕显得啰嗦而放弃**。

> 本节 2026-08-18 补入，来源是一次真实往返：知了hub 执行者在执行中把 `!.env.example` 放宽为 `!.env*.example`（不改则新建的模板文件会被静默排除），并连续三轮记录「此事仍悬着」。指挥师确实在与用户的对话里写过「我确认、采纳」，但那句话从未出现在转发给执行者的文本中——**三轮追问，事后证明每一轮都对**。
> 这条口径此前只写在仓库外的指挥师手册里，而它约束的是执行者行为；**由执行者指出后才补进两份仓库手册**——与 `v2.1` 越权同一个根因：规则存在，但不在必须照做的那个角色读得到的地方。

### 1.2.4 两个执行者的分工：实施方与验证存档方

每个项目现在有**两个执行者**，职责不同——**开工前先确认本轮你是哪一个**：

| 角色 | 通常是谁 | 做什么 |
|---|---|---|
| **实施方** | Codex | 按指令改动；写 CHANGELOG 中「改了什么 + 实测证据」那部分。**改完停在未提交状态**，不提交、不推送 |
| **验证存档方** | Claude Code | **独立验证**实施方的改动；写 CHANGELOG 中「我怎么证实的」那部分；然后提交、推送、打标签 |

**两条不可放宽：**

1. **两份记录，不是一份。** 验证方**不要复述实施方的话**——用你自己的方法重新证实（剔除法、分段 SHA-256、落盘探针都行），写你**实际验到的**。实施方在现场、握有实测数字；验证方不在现场、但视角独立。**同一件事两个独立来源，比一个来源写两遍有价值得多。**
2. **每轮写权限只归一个执行者。** 指令里会点名本轮谁持有。**发现工作区有另一个执行者的未提交改动，停下报告，不要在其上叠加改动。**

角色可以按轮次调换，也可能由同一个 agent 兼任两侧——**以本轮指令写明的为准**。不要假设上一轮你是哪个角色、这一轮就还是。

### 1.4 两个仓库的协作边界

编辑根目录下有两个独立仓库：

| 仓库 | 职责 | 当前审计基线 |
|---|---|---|
| `zhiliaohub/` | 主站静态前台、`admin-server`、部署配置和主站文档 | v2.0 |
| `zhiliaohub_app/` | 原生 Android 管理助手 | v0.3 |

协作时必须遵守：

1. 两个仓库分别检查 `git status`、历史、标签和远程，不把共享编辑根目录误当成一个 Git 仓库。
2. 用户只授权一个仓库时，不修改另一个仓库；跨仓库任务必须在指令中分别列出范围。
3. 两仓库独立提交、独立打标签，版本号不强行对齐。
4. 服务端设备认证协议发生破坏性变化时，必须同步检查 `admin-server/README.md` 的最低兼容说明，并评估 App 是否需要改动。
5. App 的 UI、网络容错或构建变体变化如果不改变接口，不应顺带修改主站。
6. 跨仓库任务可以由同一执行 agent 处理，也可以拆给不同 agent，但每个仓库必须有独立的工作区核对、文件清单、验证、提交和CI结论，不能用一个仓库的结果代替另一个仓库。

### 1.5 文档权威性原则

文档是导航，不是比代码和运行结果更高优先级的事实源。若文档、代码、Git 历史和线上行为不一致，先停止引用过期结论，列出差异，再决定本轮是否修正文档或代码。

### 1.6 本机运行 compose 的约束

服务器不归你（见 1.2.1），但**本机跑 compose 归你**——改 `docker-compose.yml`、`deploy/nginx.conf` 或 `Dockerfile` 时你会在本地验证。以下两条与在哪台机器上跑无关，只与「跑 compose」这个动作有关：

1. **禁止输出完整 `docker compose config`。** 含真实 `env_file` 时它会展开全部密钥。语法验证只用 `--quiet`；**也不要用 `--format json` 再管道过滤**——密钥已经进了进程输出，过滤只是没显示出来。
2. **`docker compose up -d` 不重建已有标签镜像**，也不因挂载内容变化而重建容器。代码、依赖、Dockerfile 或挂载内容变化后必须显式 `build`，必要时加 `--force-recreate`；**「容器 healthy」不能单独作为版本正确的证据**——要查渲染后的实际配置。

> 第 2 条来自本项目 v2.0 部署实测：`nginx -t` 通过、5 个入口全 200、容器 healthy，但渲染出的配置里 `set_real_ip_from` 一条都没有。

### 1.7 开工前的 Git 检查

对**本轮涉及的每个仓库**分别执行 `git status` 与 `git log origin/<分支>..<分支>`，**确认没有未推送的本地提交**。若有，先报告并等指挥师处置，不要在其上继续叠加改动。

这一条是强制的：未推送的本地提交会让「仓库实际状态」与「文档记录的状态」悄悄分叉，而分叉通常要到下一次部署或存档才暴露，因此该检查不得依赖偶然发现。

> 本仓库主分支为 `main`，即 `git log origin/main..main`。`zhiliaohub_app` 参与本轮时单独检查、分支名以该仓库实际为准；两个仓库不得用一个的结果代替另一个（见 1.4）。
> 该规则源自同机另一个项目的真实事故：某版本收尾期间**连续三次**发现未推送的本地提交，导致状态记录与实际代码不一致。

### 1.8 地址与主机名的公开边界（写入任何文件前必读）

本仓库是**公开仓库**。和知天不同，知了hub 的域名本来就是公开信息——**真正必须留在仓库外的是源站真实 IP**：

| 内容 | 能否写进仓库 |
|---|---|
| 主站域名、小作坊子域名 | ✅ **可以**。它们挂着 DNS、任何人都能访问，藏没有意义 |
| 知天的**客户端**主机名（前台跳转入口要用） | ✅ **可以**。同属公开入口 |
| **源站真实 IP** | ❌ **禁止**出现在任何受版本控制的文件、CHANGELOG 或提交信息中 |
| 服务器路径、容器内绝对路径、真实凭据 | ❌ **禁止** |
| 知天的**企业管理后台**主机名 | ❌ **禁止**。它在知天那边是刻意不公开的面，不因为换了个仓库就变公开——需要指代时写「知天企业管理后台主机名」 |

**为什么源站 IP 在接 Cloudflare 之后才变关键**：站点由 Cloudflare 代理，域名解析到的是 CF 边缘。**但源站可被直连**（实测 `https://<源站IP>/` 返回 200），一旦 IP 公开，任何人都能绕过 Cloudflare 的 WAF 与 DDoS 吸收，直接打源站——等于亲手取消这层保护。接 CF 之前 IP 泄露只是暴露服务器，接了之后它还额外作废了一整层防护。

**部署配置里的处理方式**：`deploy/` 下受版本控制的文件用占位符或环境变量，真实值只进被 Git 忽略的 `.env` 与服务器现场。这与 1.4 的仓库边界、以及 5.6 的安全与隐私要求是同一套原则的不同面。

> **本节 2026-08-18 补入。** 此前该边界只写在知天手册（那边保护的是管理后台主机名），本仓库只有散落的「不写真实凭据/IP」，**规则只落单边**。两个项目要保护的东西不同——知天是一个主机名，知了hub 是源站 IP——所以本节按本仓库自身情况另写，不是照抄。

### 1.9 跨项目工作时的边界

你可能被授权**同时在两个项目里工作**（典型是设计取向任务：视觉语言要跨站一致，交给同一只手比派两次再核对可靠）。这时以下边界必须守住。

#### 禁区：`D:\zhiliao\` 下只有两个目录可动

根目录有 **14 个条目**（`.workbuddy\` 是隐藏目录，`ls` 不加 `-A`、资源管理器默认设置下都看不到，容易漏数），你只能动其中两个：

| 可动 | `zhiliaohub\`、`zhitian\` |
|---|---|
| **一律不读、不写、不引用** | `与指挥师的对话\`、`zhiliao1.0\`、`zhiliao1.1\`、`zhiliao1.3\`、`zhiliao1.4\`、`diandian\`、`my1234\`、`opendesign\`、`zhili\`、`zhimian\`、`学习知了\`、`.workbuddy\` |

三类风险各不相同：

- **`与指挥师的对话\`** 含**真实服务器 IP、服务器路径、SSH 别名与证书信息**。你在根目录**能看见它，但看见不等于可以用**——一旦其中的真实值被写进任一仓库，两份手册关于地址与主机名的规定当场作废。需要服务器上的事实时**向指挥师要**。
- **`zhiliao1.0` / `1.1` / `1.3` / `1.4`** 是**历史版本**。照着它们改会引入已废弃的实现；`zhiliao1.4\` 还带着自己的 `AGENTS.md` 与 `CLAUDE.md`——**那是另一个项目的 agent 指令，不是给你的**。
- 其余是无关项目、学习材料，以及已停用角色留下的工具目录 `.workbuddy\`。

**需要参考历史实现时，用当前仓库的 `git log`，不要去翻那些目录。**

#### 不要把一个项目的参数套用到另一个

两个项目的工程参数**在多处相反**，凭印象套用会出真实故障：

| 参数 | 差异 |
|---|---|
| 主分支 | 知了hub 两个仓库都是 `main`；知天 `zhitian`／`zhitian_admin`／`zhitian_app` 是 `master`，**但 `zhitian-deploy` 是 `main`** |
| 服务器拉取纪律 | 两个项目**相反**——一个跟随分支，一个必须 `checkout` 到具体标签。**绝不可互相套用** |
| CHANGELOG 排序 | 知了hub 三个仓库都是**新在上**；知天三个应用仓库是**旧在上**，**但 `zhitian-deploy` 是新在上** |
| 测试与语法检查 | 命令完全不同 |
| CHANGELOG 条目格式 | 一边有 bullet 条数上限，一边没有 |

**每次动手前，读你正在改的那个项目自己的手册，不要凭另一边的印象。** 拿不准就在回报里问，不要猜。

#### 存档仍按仓库分开

跨项目工作**不改变存档粒度**：每个仓库独立 `git status`、独立文件清单、独立提交、独立报告。**不得用一个仓库的验证结果代替另一个仓库**，也不得把两个项目的改动写进同一条 CHANGELOG 条目。

## 五、知了hub 编码、内容与运行规范

知了hub 由两套技术边界组成：访客前台仍是原生 HTML/CSS/JavaScript 的零构建静态站；`admin-server` 是独立 Node.js/Express 后台。前台规范不能直接替代后台的认证、数据和错误处理规范，后台依赖也不应无必要渗入访客前台。

### 5.1 通用原则

1. 文件保持 UTF-8；命名、注释、提示文案与现有中文语境一致。
2. 修改前先读真实文件和 `git status`，保留用户已有改动，不使用破坏性 Git 命令清理工作区。
3. 复用现有服务、模板、上传策略、认证中间件和视觉系统，不为相同能力另建第二套实现。
4. 不硬编码密码、哈希、session 密钥、TOTP 密钥、真实服务器路径或其他凭据。
5. 不把测试样例、占位内容或推测值写成真实数据。
6. 新能力必须写明数据源、写入点、公开面、失败行为和验证边界。

### 5.2 前台 HTML 与静态生成

1. 前台继续使用多个独立 HTML 文件，不引入 SPA、前端框架或构建链，除非先完成架构讨论。
2. 使用 `header`、`nav`、`main`、`section`、`article`、`footer` 等语义元素；每页一个主要 `h1`，标题层级连续。
3. 导航、按钮和表单必须有可理解的可访问名称；字段使用真实 `label`，动态结果使用适当的 `aria-live` 或 `role="status"`。
4. 站内链接使用可部署的相对路径；图片有符合用途的替代文本；新窗口外链同时使用 `rel="noopener noreferrer"`。
5. `works.html`、`works-*.html`、作品分类页、`notes.html`、`notes-*.html` 和 `feedback.html` 属于发布生成物。顶部带“请勿手动编辑”标记的文件只能通过数据库/Markdown、`admin-server/src/templates/` 和 `publish-service.js` 改变。
6. `index.html`、`tools.html` 等手写页修改共享导航时，必须同步生成模板并重新发布，防止手写页和生成页出现两套导航。
7. 页面加载继续以静态文件为主；当前访客运行时写请求仅限反馈提交。不得为内容读取额外引入后台实时 API。

### 5.3 前台 CSS

1. 公共视觉写入 `css/style.css`，复用现有自定义属性、间距、色彩、圆角和水泥灰/雾蓝灰体系。
2. 布局优先使用 Grid、Flexbox、`clamp()` 和 scroll-snap 等原生能力；至少覆盖桌面和约 390px 窄屏。
3. 不允许页面级横向溢出；作品分组等明确设计的局部横向滚动容器除外。
4. 动效支持 `prefers-reduced-motion`，装饰动画不能阻塞内容和交互。
5. 不使用内联样式解决应复用的布局问题，不为单页复制大段共享规则。

### 5.4 前台 JavaScript

1. 公共交互放在 `js/site.js`，首页 Canvas 放在 `js/particles.js`；使用原生浏览器 API，不无必要引入第三方库。
2. 共享脚本按页面能力检查元素是否存在，在不含对应组件的页面也不能报错。
3. 避免污染全局；事件绑定考虑重复初始化、键盘操作、触摸与鼠标差异。
4. 用户可控文本优先使用 `textContent`，不得未经转义直接拼入 `innerHTML`。
5. 反馈提交必须如实区分待审核、校验错误和限流；蜜罐命中时对自动提交者保持与正常受理相同的外部响应。
6. Canvas 动画继续遵守 DPR、帧率、数量、页面隐藏/视口外暂停和减少动态效果等性能边界。

### 5.5 `admin-server` 编码规范

#### 路由与服务分层

- `src/server.js` 只负责启动、网络提示、调度器接入和优雅关闭。
- `src/app.js` 负责 Express 应用装配、路由、中间件、认证/CSRF门禁和统一错误响应；不要把复杂业务继续堆进路由处理器。
- 数据校验与业务操作放在 `src/services/`；页面字符串与静态生成放在 `src/views.js`、`src/lib/html.js` 和 `src/templates/`。
- 项目当前使用 CommonJS（`require`/`module.exports`）和 Node.js 22+；没有经过整体迁移决定，不在局部混入另一套模块体系。

#### SQLite 与文件内容

- SQLite 由 `better-sqlite3` 管理，启动时启用 WAL、外键和 busy timeout；查询使用预编译语句，成组写入使用事务。
- 新表/新字段必须同时考虑 `data/schema.sql` 的新库定义和 `db.js` 的旧库升级路径。
- 一次性数据迁移必须幂等、有迁移标记或等效防重复机制；真实执行前先做只读预览并取得用户确认。
- 作品/日记结构化元数据在 SQLite，正文在 Markdown；服务层保持二者一致并使用原子文件替换。
- 当前内容写入只保证单进程内按记录串行，不得描述为多实例并发安全。部署仍应保持单个后台实例，除非另行设计共享锁和数据层。

#### 认证、会话和密钥

- 管理后台保留密码+TOTP与设备挑战应答两条认证路径；高风险管理操作若现有规则要求密码+TOTP，不得因设备会话方便而放宽。
- 管理写接口继续要求已认证会话与 CSRF；公开反馈和设备认证接口使用各自的限流、一次性凭证和输入校验。
- session 使用 SQLite 持久化，Cookie 保持 `httpOnly`、`SameSite=Strict`，生产环境使用 `Secure`。
- 管理员密码只保存 bcrypt 哈希；TOTP 密钥加密保存；Android P-256 私钥只存在设备 Keystore，服务端只保存公钥。
- 密钥来自服务器现场的 `admin-server/.env`，不提供不安全默认值，不写入日志、文档、测试快照或 Git 历史。

#### 上传、小作坊和发布

- 上传继续复用扩展名、MIME、文件签名和大小上限的组合校验，不能只信任客户端文件名。
- 备份只收 `uploads/` 下的非ZIP文件；被排除ZIP必须在 `manifest.excluded` 记录路径、大小和SHA-256，恢复时明确提示用户从本地补齐，不得静默缺失。**一份“静默地少了东西”的备份比没有备份更危险。**
- 小作坊 ZIP 必须在写出前完成路径穿越、解压总量、文件数、扩展名、符号链接和加密条目检查；失败时拒绝整个包。
- 发布采用全量同步，清理范围必须受自动生成标记或受控媒体目录约束；不得扩大到 `index.html`、源码、配置或其他非目标文件。
- 发布失败必须恢复发布前状态，不把半完成静态文件暴露给访客。

#### 日志与错误处理

- 预期的校验/业务错误返回明确中文提示和合适 HTTP 状态；未知异常对用户只返回通用错误，详细异常仅进入服务器日志。
- 日志不得记录密码、TOTP、配对码、挑战签名、Cookie、CSRF、邮箱全文、备份密码或密钥材料。
- 定时备份、镜像同步等后台任务失败不能静默；日志应写明失败动作、影响和最后成功状态，但不得泄露敏感配置。
- 新的公开接口要审查是否会通过错误差异、响应时间或隐藏字段泄露审核状态、账号存在性或反滥用规则。

#### 测试

- 后台语法基线运行 `npm run check`，完整回归运行 `npm test`。
- 新功能至少覆盖成功、校验失败、认证/CSRF失败、数据一致性和清理/回滚；安全边界要有专门的反例测试。
- 测试使用隔离数据库和临时目录，不读写真实 `.env`、SQLite、上传、备份、内容或小作坊目录。
- GitHub Actions 当前只检查全仓 JavaScript 语法和 HTML 本地引用，不能用 CI 通过代替本地后台测试。

### 5.6 安全、隐私与真实运行面

旧版手册把安全、隐私、日志和错误分级列为“当前不适用”，理由是项目没有后端。这个理由已经失效。知了hub 不照搬知天的 Pydantic、角色模型或 API Key 规范，但必须维护适合自身运行面的原则：

1. **最小公开面：** Nginx 只公开静态站点和明确的 `/admin`、`/api`、`/uploads`、`/health` 路径；后台端口不直接发布到公网。
2. **先审后发：** 反馈新提交一律 `pending`；发布查询在 SQL 层只读取 `approved`，邮箱和 IP 永不进入前台 HTML。
3. **最小数据披露：** IP 只用于限流和滥用追踪；日志和错误响应不泄露凭据、内部路径或堆栈。
4. **上传不可信：** 浏览器提供的扩展名、MIME、ZIP目录和压缩后大小都不能单独作为安全依据。
5. **密钥不入库：** 两层 `.env` 各司其职；真实 `.env`、数据库、上传、备份和 `lab-storage` 运行数据必须被 Git 排除。
6. **代理信任明确：** 线上 Nginx 转发真实 IP 与协议，后台只信任配置的单跳代理；改变代理层数必须同步审查限流与 Secure Cookie。
7. **破坏性恢复有安全网：** 恢复前自动快照、校验和、可选加密和显式 `--force` 都不得绕过；若用户要求跳过快照，必须再次说明不可逆风险。
8. **部署事实单独验证：** 仓库有配置不代表服务器已更新；本地镜像通过不代表 DNS、TLS、Cookie 隔离和来源 IP 已在线上通过。

### 5.7 内容真实性与产品边界

1. 反馈提交只能显示“已提交审核”，不能显示“已发布”。
2. 无真实内容时显示明确空状态；不制造阅读量、下载量、用户评价或上线日期。
3. 下载和体验按钮只在作品数据确实具备相应资源时渲染。
4. “智能工具”当前是说明页，不包含知天登录、注册或真实工具集成，不得伪装可用入口。
5. 知天是独立项目；本仓库不存放其业务代码、账号数据或服务配置。
6. 小作坊本地 `/lab/` 服务与真实独立子域名是不同验证层级；Cookie、TLS 和域名隔离必须在线上复核。

### 6.1 何时需要同步 `zhiliaohub_app`

以下情况需要把 App 纳入评估，但仍须用户明确授权后才能修改 App 仓库：

- `/api/device-auth/*` 的路径、请求体、响应字段、状态码或签名载荷变化；
- session Cookie 名称、作用域或认证失效语义变化；
- `/health` 或 App 使用的会话探测接口变化；
- TLS、明文 HTTP、重定向或代理规则改变 App 可达方式；
- 最低兼容版本需要更新。

纯前台视觉、内容发布、反馈审核后台、小作坊展示或备份内部实现通常不需要修改 App。反过来，App flavor、图标、客户端重试或本地 UI 变化通常不需要修改主站，除非协议或兼容说明发生变化。

## 七、验证规范

验证范围随改动风险增加，不能用低层级验证替代高层级结论。

### 7.1 文档改动

- 通读完整文档，检查内部逻辑、日期、版本、路径、命令和 Markdown 表格。
- 对照真实文件、`git log`、标签、配置和运行结果；不能只在三份文档之间互相引用。
- 如果发现其他文档需要大范围重写，先列出偏差，未经用户确认不扩大本轮范围。

### 7.2 前台和静态发布

- JavaScript 使用 `node --check`；HTML 执行本地相对引用检查。
- 页面/样式改动至少检查桌面和约 390px 窄屏、控制台、页面级横向溢出和真实链接。
- 共享导航、CSS 或 JS 改动要覆盖首页、作品一级/二级/详情、日记列表/详情、反馈和工具页。
- 发布链路改动必须在隔离数据中真实全量发布，检查生成标记、旧页/旧媒体清理和失败恢复。
- 反馈发布还要搜索生成源码，确认 pending/rejected、邮箱和 IP 不存在。

### 7.3 后台代码

- 在 `admin-server/` 运行 `npm run check` 与 `npm test`。
- 改动单个未被 `npm run check` 列出的 JavaScript 文件时，额外运行 `node --check <文件>`；新增文件应同步纳入检查脚本或全仓语法检查。
- 认证、上传、反馈、发布、备份等交互除自动化测试外，还应在真实浏览器操作受影响主路径，并检查未登录、CSRF、错误提示和控制台。
- TOTP、设备配对、生物识别等需要用户设备操作的环节，要逐项记录用户真实反馈，不代替用户宣称通过。
- 测试必须隔离真实数据。若任务要求操作真实 SQLite，先备份/只读预览并等待明确确认。

### 7.4 部署配置和线上变更

部署验证分四层，报告必须写清完成到哪一层：

1. **静态审阅：** 核对 YAML/Nginx 语法、占位变量、挂载、权限、路由和凭据排除。
2. **配置解析：** 使用现场或无敏感占位 `.env` 运行 `docker compose config --quiet`；Nginx 使用 `nginx -t` 或官方容器检查。
3. **本地容器：** Dockerfile、依赖、挂载、启动命令或运行时路径变化时，实际 `docker compose build`（必要时 `--no-cache`）和 `docker compose up`，验证 health、持久化与重启。`docker compose up` 不会保证自动重建最新镜像。
4. **真实部署：** 只有实际服务器上的 DNS、TLS、HTTP→HTTPS、静态站、后台登录、真实来源 IP、Secure Cookie、上传、发布、备份和小作坊独立主机名检查通过，才能写“线上通过”。

如果任务明确限定为“只准备配置、不执行部署”，或环境确实缺少 Docker/Nginx，可以只完成前两层中的可用部分，但必须列出未执行项。涉及 Dockerfile、依赖或容器运行语义的改动，原则上应完成本地实际构建；做不到时不能把静态审阅表述为可部署验证。

### 7.5 Android App 与跨仓库

- App 改动在 App 仓库运行对应 flavor 的构建、JVM 测试和 Lint；涉及设备行为时安装到真机。
- prod/qa 两个包的构建、设置、Keystore、Cookie 和配对状态分别验证，不能从包名隔离理论直接写成真机通过。
- 网络容错的单元测试不能替代真实 WiFi/移动网络/代理切换观察；无法稳定复现的偶发故障要明确记录。
- 服务端与 App 联调要记录两边版本、接口、地址和实际操作步骤；两边 Git 状态与提交分别处理。

### 7.6 证据表述

- “无控制台错误”“无横向溢出”“链接到达目标”“数据未丢失”应有工具或真实操作支持。
- “测试通过”写明命令和数量；“CI通过”写明 CI 实际执行了什么，不能暗示它覆盖未运行的测试。
- “已部署”与“线上可用”写明实际域名、健康检查和关键交互；仅有 Compose/Nginx 文件不够。
- “理论上改善”与“真实复现通过”分开记录。

### 7.7 判断文件是否被 Git 忽略

判断某个文件会不会被 `.gitignore` 挡住，**不能靠读 `.gitignore` 推断**，也不能想当然用 `git check-ignore` 的退出码。三个坑：

1. **不要用 `-v` 的退出码判断。** 加了 `-v` 之后，只要有任何规则命中就返回 **0**——**包括 `!` 开头的否定规则**。也就是说一个「本就不该被忽略」的文件同样返回 0，看起来像被忽略了。`-v` 只用来看命中了哪条规则，不能用来判断结果。
2. **判断用 `-q` 的退出码**：`git check-ignore -q <路径>`，**0 = 被忽略，1 = 未被忽略**。
3. **已跟踪的文件默认被跳过**，永远返回 1（看起来像「没有规则管它」）。要测已跟踪的文件必须加 `--no-index`。

**拿不准时以真实文件为准**：建一个未跟踪的探针文件，看 `git status --ignored` 把它归进 `!!`（已忽略）还是 `??`（未跟踪、`git add` 能看见），测完删掉。**这是决定性的，退出码不是。**

> **在仓库目录内创建任何含密钥的文件（备份、临时副本、导出）之前，先按上面的方法确认它会被忽略。** 2026-08-16 有人在服务器改配置时建了 4 个 `.env` 备份、含真实第三方 API 密钥，而当时的 `.gitignore` 只挡精确的 `.env`——一次 `git add .` 就会推进公开仓库。
> 本节 2026-08-18 补入。来源是两个项目的执行者在同一轮**各自独立**踩到第 1、3 条，且都没采信退出码、改用落盘探针实测证伪——原指令里「`.env.example` 应当退出码 1」的说法是错的。

## 八、`CHANGELOG.md` 条目规范

- 新条目使用“日期 + 一句话概括标题”，按现有文件的倒序方式追加在顶部。
- 记录最终能力、关键文件/数据影响、验证结果、重要决定和明确边界，不流水账复述调试过程。
- 方案变化时说明有复用价值的原因；真实发现的流程或安全缺陷不能美化省略。
- 本地、容器、真机、CI、线上分别写清；没有执行的检查不能写成通过。
- 纯错别字通常不单列；会长期影响协作、架构理解、安全或运维的文档重写应记录。
- 存档条目写明提交、标签、远程和 CI；普通工作条目默认不暗示已提交。

### 8.1 版本号与标签语义

知了hub 主仓库从 `v1.0` 到 `v2.0` 一直使用两段式版本号。自 `v2.0.1` 起，在保留原有功能版本习惯的基础上，用第三段明确标识非功能性整理：

1. **有实质代码改动或功能变化：** 继续使用 `vX.Y` 两段式标签，例如 `v2.0`、`v3.0`；阶段编号和跳号方式沿用项目既有习惯，不为套用通用语义化版本格式而强制改成三段式。
2. **只有文档或协作流程整理：** 使用 `vX.Y.Z` 三段式补丁标签，例如 `v2.0.1`。第三段表示紧跟最近一个两段式功能版本的非功能性整理；同一功能基线下如果连续发生多次此类存档，第三段依次递增。
3. **混合改动按代码变化处理：** 只要同一存档中包含实质代码逻辑、接口、数据结构、部署行为或用户可见功能变化，就不能使用文档补丁号掩盖，应按两段式功能版本处理。
4. **版本号必须能直接传达性质：** 看到两段式即可判断该存档可能包含功能/代码变化；看到三段式补丁号即可判断它只整理文档或协作流程，无需先翻提交正文才能分辨。
5. **项目之间仍然独立：** 这套约定参考知天项目已经采用的类似补丁版本语义，使两个项目的标签含义容易理解；知了hub、知天以及独立的 `zhiliaohub_app` 仍分别提交和打标签，版本号不强行对齐。

#### 什么时候才打标签

**打标不必逐轮进行。** 提交与推送是安全网、每轮照常；标签是「值得回到这里」的锚点，**攒够了再打**：

| 情形 | 是否打标 |
|---|---|
| 真实行为变化，且准备部署 | ✅ 打两段式 `vX.Y` |
| 纯文档 / 流程整理 | ⏸ **累积若干轮后合并打一个**三段式 `vX.Y.Z`，不逐轮打 |
| 一个工作主题收尾 | ✅ 打，注释里列出覆盖了此前哪几条工作条目 |
| 服务器部署前 | ✅ 打，部署需要一个可回滚的锚点 |

- **不打标的轮次**：CHANGELOG 写**普通工作条目**——日期 + 概括，**不写版本号**、不暗示已存档；提交与推送照常进行。
- **打标的那一轮**：写**存档条目**，注明提交、标签、远程，并说明该标签**覆盖了此前哪几条工作条目**。

> **该约定 2026-08-18 由用户提出。** 起因是**四天内（08-15～08-18）打出了 9 个三段式补丁标签**（知了hub 4 个、知天 5 个），**全是文档整理，没有一个标记出真正不同的状态**。**标签一经推送不删不重打**，噪声会永久留在标签列表里。数字经 `git for-each-ref` 核实——初稿我凭印象写的「两天内六个」，天数和个数都不对。
> 需要注意的是：区分「存档条目 / 普通工作条目」这件事**知了hub 八章本来就写着**，只是此前每轮都被当成存档条目处理——**规则在手册里，执行时没照做**。

## 九、更新项目记忆与结构文档

### 9.1 `claude_memory.md`

它记录“现在”，不是无限增长的历史：

1. 更新日期、当前版本、运行状态和本轮验证。
2. 删除已经完成的待办，把尚未验证的部分留在明确边界中。
3. 不把旧版本号、旧测试数量、旧 App 兼容版本或部署前状态长期保留为当前事实。
4. 跨仓库状态只写经过对应仓库核实的版本和边界。

### 9.2 `zhiliaohub_structure.md`

它记录技术设计：

1. 架构、数据流、目录职责、部署拓扑和安全边界变化时同步。

### 9.3 四份文档的分工

**`claude_memory.md` 记录现在，`CHANGELOG.md` 记录过去，`zhiliaohub_structure.md` 记录技术设计，本文记录如何协作与验证。**

当四者冲突时，以真实代码、Git 历史、数据和运行证据重新校准，而不是选择对当前任务最方便的一份描述。

## 十、存档操作规范

Git 提交、推送和标签属于严格执行任务，默认由你完成（依据见 1.2.2），并遵循：

1. 分别在每个目标仓库运行 `git status`、检查差异和忽略规则，确认没有运行时数据、构建产物、真实凭据或跨仓库误改。
2. 在写入Git历史前向用户列出完整文件清单；提交、推送和打标签各需授权，**用户可以一并授权**；但**发现问题必须停下**，不得带着已知问题继续。授权存档不自动包含部署。
3. 使用明确文件路径暂存，不用模糊的全仓清理或破坏性Git命令；提交标题说明结果，正文说明主要能力、验证事实和仍未验证边界。
4. 推送目标分支后，以本次完整提交哈希确认远程同步和CI触发；不能拿旧运行记录代替本轮CI。
5. 只有用户明确指定版本与标签信息时才创建带注释标签，并确认标签指向预期提交后单独推送。
6. 最终报告提交哈希、远程分支、标签（如有）、CI链接、工作区状态，以及是否仍需生产更新。多个仓库必须分别报告。
